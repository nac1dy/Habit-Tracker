== 3. Wichtigste Lernergebnisse aus Sprint 3
[cols="1,3", options="header"]
|===
| Kriterium | Ihre Antwort

| asynchrone Entwicklung
| Wir haben bei der Umsetzung festgestellt, dass eine getrennte Entwicklung von Frontend und Backend zu schlecht ausgearbeiteten Schnittstellen führt. Ein nützliches Inkrement lässt sich deutlich einfacher integrieren, wenn Features vertikal und durchgängig abgearbeitet werden.

| lokale Speicherung
| Unsere Annahme, Inhalte rein lokal speichernzukönnen, hat sich als problematisch erwiesen. Da Nutzer eine geräteübergreifende Verfügbarkeit bevorzugen und das Risiko eines Datenverlusts minimiert werden muss, erfordert unser Produkt eine serverseitige Alternative.

| Qualität durch Gruppenarbeit
| Da zeitversetzte Code-Reviews von unbeteiligten Teammitgliedern meist Kontextprobleme verursachten, haben wir unsere Arbeitsweise angepasst. Eine gemeinsame Bearbeitung von Aufgaben mit anschließendem Review innerhalb der Gruppe führten zu einem tieferen technischen Verständnis und fundierterem Feedback.
|===

== 5. Produktinkrement, Verifikation und Umsetzungsqualität
[cols="1,3", options="header"]
|===
| Kriterium | Ihre Antwort

| Umgesetzter End-to-End-Nutzerfluss
| Das Produktinkrement ist lokal ausführbar und erfüllt ein zentrales Nutzerziel. Nutzer können das Dashboard öffnen, Gewohnheiten anlegen und mit einem einzigen Klick abhaken.

| Akzeptanzkriterien und Definition of Done
| Wir haben bei jedem Ticket unsere festgelegten Akzeptanzkriterien praktisch getestet. Vor dem Schließen eines Issues haben wir geprüft, ob unsere Definition of Done komplett erfüllt ist, beispielsweise ob der Code von der Gruppe abgenommen wurde und fehlerfrei läuft.

| Akzeptanzorientierte Verifikation
| Wir haben die erwarteten Normalfälle für unsere Kernfunktionen durchgespielt, wie etwa das erfolgreiche Speichern und Abhaken von Gewohnheiten.

| Code Review, Integration und main branch
| Jede neue Funktion wurde erst über einen Pull Request in unsere gemeinsame Code-Basis integriert, nachdem sie von verantwortlichen Teammitgliedern überprüft wurde. Durch diese Code-Reviews stellen wir sicher, dass unser Haupt-Branch jederzeit stabil und lauffähig bleibt.

| Wartbarkeitsverbesserung / Refactoring
| Weil wir am Anfang Frontend und Backend zu stark getrennt entwickelt haben, sind ungenutzte Schnittstellen entstanden. Diese losen Anschlüsse haben wir durch gezieltes Refactoring entfernt und doppelten Code zusammengefasst. Dies erleichtert uns die Wartung der Anwendung und vermeidet unklare Strukturen im Code.

| User-Flow- oder Usability-Check
| Wir haben unsere App aus Nutzersicht getestet und geprüft, ob das Abhaken von Gewohnheiten wirklich so schnell geht, wie wir es in unserem UX-Konzept geplant haben. Wir kamen unter anderem zu dem Ergebnis, dass unsere Web-Application flüssig reagiert und den Nutzer nicht durch unnötig ausbremst.
|===
