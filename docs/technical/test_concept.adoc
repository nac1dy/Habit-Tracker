== Teststrategie

Unsere Teststrategie basiert auf der Entscheidung, dass wir die Qualität der wichtigsten Komponenten der Anwendung sicherstellen wollen. Deswegen liegt der Fokus auf Unit-Tests, die die Geschäftslogik isoliert prüfen. Allerdings werden wir auch Integrationstests für kritische Schnittstellen und Datenbankzugriffe eingesetzen.

== Teststufen

=== Unit-Tests

Unit-Tests prüfen einzelne Klassen oder Funktionen isoliert voneinander.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Sicherstellung der korrekten Funktionsweise einzelner Komponenten in Isolation

| Umfang
| Alle Service- und Domänenklassen; Fokus auf Geschäftslogik

| Werkzeug
| Ideen: Vitest

| Mocking (Faken / Simulieren)
| Ideen: vi.mock(Vitest)

| Abdeckungsziel
| Mindestens 70 % Zeilenabdeckung auf der zentralen Geschäftslogik

| Ausführung
| Lokal während der Entwicklung und automatisiert über GitHub Actions bei jedem Push in das Repository
|===

=== Integrationstests

Integrationstests prüfen das Zusammenspiel mehrerer Komponenten, z. B. Service und Datenbank.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Ziel
| Sicherstellung der korrekten Kommunikation zwischen Komponenten und mit externen Systemen

| Umfang
| Prüfen der Datenbankzugriffe und API-Endpunkte, die mehrere Komponenten involvieren

| Werkzeug
| Vitest (Integrationstest), Supabase JavaScript Client für Datenbankzugriffe

| Testdaten
| Separate Supabase-Testdantenbank?

| Ausführung
| Optional Lokal und automatisiert über GitHub Actions bei jedem Push in das Repository
|===

== Testabdeckung

_Definiert die angestrebten Mindestwerte für die Testabdeckung._

[cols="1,1,2", options="header"]
|===
| Schicht | Zielwert | Bemerkung

| Service-Schicht
| ≥ 70 %
| Fokus auf Geschäftslogik (höchste Priorität)

| Persistenz-Schicht
| ≥ 50 %
| Grundlegende CRUD-Operationen und Datenbankzugriffe durch Integrationstests abgedeckt

| Controller / API
| ≥ 60 %
| Zentrale API-Funktionen, sowie Fehlerbehandlung überprüft

| Frontend-Komponenten
| ≥ 50 %
| Fokus auf wichtigste React-Komponenten und deren Interaktionen
|===

NOTE: Abdeckung ist kein Selbstzweck. 80 % sinnlose Tests sind schlechter als 60 % gut durchdachte Tests. Qualität der Tests ist wichtiger als der Prozentwert.

=== Ausführung der Tests
==== Lokale Entwicklung
[source,bash]
----
# Alle Unit-Tests ausführen
[z. B.  pytest  |  npm test]

[z. B.  pytest --cov]

==== CI-Pipeline

Tests werden automatisch bei jedem Push im Repository ausgeführt. Je nach Testart können unterschiedliche Trigger und Umgebungen sinnvoll sein. Die Konfiguration der CI-Pipeline sollte sicherstellen, dass alle Tests zuverlässig und schnell ausgeführt werden.

=== Definition of Done

//Bitte anpassen und nur das aufnehmen, was tatsächlich auch durchgeführt wird.
Folgende Testkriterien sind Teil unserer Definition of Done:

* [ ] Alle bestehenden Tests sind grün
* [ ] Neue Funktionalität ist durch Unit-Tests abgedeckt
* [ ] Die Mindest-Testabdeckung wird nicht unterschritten
* [ ] Manuelle Tests für neue Features wurden durchgeführt
* [ ] Keine bekannten kritischen Fehler sind offen

== Fehlerbehandlung & Bugtracking
NOTE: Noch nicht Bearbeitet -> Besprechen

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Wo werden Bugs erfasst?
| Als Issue mit Label "Bug" in GitHub Issues mit Angabe der betroffenen Komponente und Reproduktionsschritten

| Priorisierung
| kritische Bugs (Bugs die, die Kernfunktionen beeinträchtigen oder Nutzerdaten beinhalten) werden sofort im laufenden Sprint behoben; andere ins Backlog

| Reproduzierbarkeit
| Jeder Bug-Report enthält Schritte zur Reproduktion, erwartetes und tatsächliches Verhalten und Beschreibung (In welchem Branch)
|===

_Dieses Testkonzept wird bei Bedarf aktualisiert — insbesondere wenn neue Testarten eingeführt,
Werkzeuge gewechselt oder Abdeckungsziele angepasst werden._
