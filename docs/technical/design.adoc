== Systemübersicht & Schichtenarchitektur

_Dieser Abschnitt beschreibt, in welche Schichten oder Bereiche das System aufgeteilt ist
und welche Verantwortung jede Schicht trägt. Eine klare Schichtentrennung verhindert,
dass Geschäftslogik, Datenzugriff und Präsentation unkontrolliert vermischt werden._

=== Beschreibung der Schichten

[cols="1,2,2", options="header"]
|===
| Schicht | Verantwortung | Darf abhängen von

| Präsentationsschicht
| Darstellung der UI; Verarbeitung von Nutzereingaben; Entgegennahme von HTTP/REST-Anfragen
| Anwendungsschicht

| Anwendungsschicht
| Verarbeitung und Koordination der Geschäftslogik und Datenbankzugriffe; Authentifizierung
| Domänenschicht, Persistenzschicht

| Domänenschicht
| Fachliche Entitäten und Regeln kapseln;
  Invarianten sicherstellen (-> Value Objects);
  Kernlogik unabhängig von Infrastruktur halten
| Keine äußeren Schichten

| Persistenzschicht
| Konsistente und dauerhafte Speicherung und Verwaltung von Daten; Datenbankzugriffskapselung
| Domänenschicht (Entitäten)
|===

IMPORTANT: Die Domänenschicht darf *nicht* von Persistenz- oder Präsentationsschicht
abhängen!

=== Habit erstellen

_Der folgende Ablauf zeigt den zentralen Use Case "Habit erstellen". Dadurch, dass der Habit-Manager als Web-Service implementiert wird, laufen die meisten Interaktionen über HTTP-Requests ab._

_Dieser Interaktionsfluss ist sehr relevant, da er die zentrale Funktionalität des Systems darstellt._

[plantuml, sequence-booking, svg]
....
@startuml
skinparam monochrome true
skinparam defaultFontSize 12

actor "Nutzer:in" as user
participant "Visualizer" as ctrl
participant "Habit-Manager" as svc
participant "Datenbank" as repo
participant "Benachrichtigungs-\nService" as notify

user -> ctrl : Post /habit{name, category, intervall}
ctrl -> ctrl : Eingabe validieren
ctrl -> svc : createHabit(name, category, intervall, habitid)
svc -> svc : checkForProblems(habitid)
svc --> svc : true
svc -> repo : saveHabit()
repo --> svc : savedHabit
svc -> notify : confirmCreation()
notify --> svc : OK
svc --> ctrl : Habit
ctrl --> user : 201 Created\n{habitid, details}

@enduml
....

'''

=== Fehlerfluss-Szenario: Habit existiert bereits

_Falls ein Nutzer versucht, einen bereits existierenden Habit zu erstellen, soll eine Fehlermeldung angezeigt werden und der Erstellungsprozess abgebrochen werden._

[plantuml, sequence-conflict, svg]
....
@startuml
skinparam monochrome true
skinparam defaultFontSize 12

actor "Nutzer" as user
participant "Habit-Manager" as ctrl
participant "Datenbank" as repo

user -> ctrl : Post /habit{name, category, intervall}
ctrl -> ctrl : createHabit(name, category, intervall, habitid)
ctrl -> repo : checkForProblems(habitid)
repo --> ctrl : false
ctrl --> ctrl : HabitAlreadyExistsException
ctrl --> user : 409 Conflict\n{message, alternativen}

@enduml
....

| Repository Pattern
| Persistenzschicht: alle Datenbankzugriffe

=== Fehlerbehandlung

[cols="1,3", options="header"]
|===
| Aspekt | Konvention

| Fachliche Fehler
| Als eigene Exception-Klassen modellieren
  (z. B. `HabitNotFoundException`)

| HTTP-Fehlercodes
| lt. offiziellem Web-Standard: 400 für Validierungsfehler; 404 für nicht gefundene Ressourcen;
  409 für Konflikte; 500 nur für unerwartete Systemfehler; ...

| Fehlermeldungen
| Immer strukturiert zurückgeben:
  `{ "fehler": "...", "details": "..." }` — kein Stack Trace an den Client

| Logging
| Fachliche Fehler als WARN; unerwartete Fehler als ERROR;
  keine personenbezogenen Daten in Log-Ausgaben (DSGVO)
|===

=== API-Konventionen

[cols="1,3", options="header"]
|===
| Aspekt | Konvention

| URL-Struktur
| Ressourcenorientiert im Plural: `/habits`, `/stats`, `/settings`

| HTTP-Methoden
| GET = lesen; POST = erstellen; DELETE = löschen

| Antwortformat
| JSON in allen Fällen; Datumsformat ISO 8601: `2026-01-01T09:00:00Z`

| Versionierung
| über URL-Präfix (z.B. `/habits/v1`); Version nur bei Breaking Changes erhöhen
|===
