== Architekturentscheidungen

_Architekturentscheidungen (Architecture Decision Records, ADRs) dokumentieren
wichtige technische Entscheidungen: Was wurde entschieden, warum, welche
Alternativen wurden verworfen, und welche Konsequenzen hat die Entscheidung._

_Jede Entscheidung, die schwer rückgängig zu machen ist oder das gesamte System
betrifft, sollte hier festgehalten werden. Kleine, lokale Implementierungsdetails
gehören nicht hierher._

NOTE: ADRs werden nicht gelöscht oder überschrieben — sie werden als
„ersetzt durch ADR-XXX" markiert. So bleibt die Entscheidungshistorie nachvollziehbar.

=== ADR-001: Next.js und Tailwind CSS als Frontend-Stack

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 2026-05-17

| *Kontext*
| Die HabitTracker-App benötigt ein Frontend-Framework für UI-Rendering, Routing,
Anwendungslogik und Web-Performance-Optimierungen. Das Team ist klein und sucht
eine bewährte, gut dokumentierte Lösung ohne hohen Konfigurationsaufwand.

| *Entscheidung*
| Wir verwenden Next.js als Frontend-Framework und Tailwind CSS als Styling-Lösung.
Next.js übernimmt Routing, SSR und Performance-Optimierungen.
Tailwind CSS ermöglicht konsistentes Styling direkt im Markup.

| *Alternativen*
| *Create React App (CRA):* Kein eingebautes SSR/SSG, schlechtere Performance out-of-the-box, weniger aktiv gewartet. +
*Vite + React:* Keine integrierten Routing- oder SSR-Funktionen ohne zusätzliche Pakete. +
*Vue.js / Nuxt:* Geringere Verbreitung im Team; kleineres Ökosystem. +
*CSS Modules / Styled Components:* Mehr Boilerplate; schwieriger konsistent zu halten als Tailwind.

| *Konsequenzen*
| (+) Integriertes Routing, SSR und Performance-Features ohne Zusatzkonfiguration. +
(+) Tailwind ermöglicht schnelles, konsistentes Styling. +
(+) Große Community; umfangreiche Dokumentation. +
(+) Kostenlos (Open Source). +
(-) Steilere Lernkurve als einfaches React (App Router, Server Components). +
(-) Tailwind-Klassen können bei komplexen Komponenten unübersichtlich werden.
|===

=== ADR-002: Supabase als Backend-Plattform (inkl. PostgreSQL)

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 2026-05-17

| *Kontext*
| Die App benötigt eine Datenbank, ein Authentifizierungssystem und REST-APIs.
Das Team hat keine Kapazitäten, ein vollständiges Backend selbst zu entwickeln und zu betreiben.

| *Entscheidung*
| Wir verwenden Supabase als Backend-as-a-Service. Supabase stellt automatisch
PostgreSQL (Datenbank), Authentifizierung (E-Mail/Passwort, OAuth),
auto-generierte REST-APIs und Row-Level Security bereit.

| *Alternativen*
| *Firebase (Google):* NoSQL-Datenbank (Firestore) – weniger geeignet für relationale Habit-Daten; Vendor Lock-in bei Google. +
*Eigenes Backend (Node.js + Express):* Zu hoher Entwicklungsaufwand; Auth, API und DB müssten komplett selbst gebaut werden. +
*PocketBase:* Weniger verbreitet; kleinere Community; weniger Integrationen. +
*AWS Amplify:* Komplex in der Konfiguration; Kosten schwer kalkulierbar.

| *Konsequenzen*
| (+) Drastische Reduzierung des Backend-Entwicklungsaufwands. +
(+) PostgreSQL ist ideal für strukturierte, relationale Habit-Daten. +
(+) Authentifizierung sofort einsatzbereit. +
(+) Open Source; kann bei Bedarf selbst gehostet werden. +
(+) Free Tier für den aktuellen Projektumfang ausreichend. +
(-) Kostenrisiko bei Wachstum (Free Tier: 500 MB DB, 50.000 MAU). +
(-) Abhängigkeit von einem externen Anbieter (Vendor Lock-in). +
(-) Supabase ist jünger als Firebase; Langzeitstabilität noch nicht vollständig bewiesen.
|===

=== ADR-003: React Built-in State Management statt Zustand

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 2026-05-17

| *Kontext*
| Die App benötigt State Management für temporäre, seitenspezifische Daten
(Formularinhalte, Toggle-Zustände, Filterwerte). Persistente Daten werden
über Supabase verwaltet (→ ADR-002). Es stand zur Frage, ob Zustand als
externe State-Bibliothek eingesetzt werden soll.

| *Entscheidung*
| Wir verwenden Reacts eingebaute Mechanismen (`useState`, `useReducer`, `useContext`)
für temporären State. Zustand und andere externe Bibliotheken werden nicht eingesetzt.

| *Alternativen*
| *Zustand:* Zusätzliche Abhängigkeit; für seitenspezifische, temporäre Zustände überdimensioniert. +
*Redux Toolkit:* Sehr mächtig, aber erheblicher Boilerplate-Overhead für den Projektumfang. +
*Jotai:* Ähnliche Stärken wie Zustand; gleiche Argumentation gegen externe Abhängigkeit. +
*Recoil:* Weniger aktiv gepflegt; unnötige Komplexität.

| *Konsequenzen*
(+) Keine zusätzliche Abhängigkeit; kleineres Bundle. +
(+) Standard-React – kein Einarbeitungsaufwand. +
(+) Einfacheres Debugging. +
(-) Bei stark wachsender Komplexität kann `useContext` zu unnötigen Re-Renders führen. +
(-) Tief verschachtelte Hierarchien können zu Prop Drilling führen. +
(-) Migration zu einer externen Lösung wäre bei starkem Wachstum notwendig.
|===
